# Production security audit (read-only)

Date: 2026-11-13. Scope: what runs in **production** (OVH Managed Kubernetes, one node, prod profile, Layerbase Postgres, Cloudflare in front, web apps on Cloudflare Workers; `docs/runbooks/ovh-production.md`, `infra/argocd/launch-set`, `infra/helm`).
Method: reading code and config, plus the safe local checks listed in section 9. Nothing was attacked, no cluster, Cloudflare, Stripe or OVH account was contacted, no secret value was read or printed (names only). The runbook itself says production was "written, never run": **every claim below about live behaviour (what Cloudflare, Envoy or Layerbase actually do) is from configuration, not from a running system.**

Verdict words: SECURE (evidence in code/config, tests exist or were run), RISK (a concrete weakness), UNVERIFIED (not seen or not run).

## 1. Executive verdict

**The identity and authorisation core is sound.** Authentication cannot be switched off by accident in the prod image (profile `prod` is baked into the image and the Helm chart; `at.security.enabled=false` exists only in `application-local.yml`), service tokens are never narrowed by `X-Acting-As` in production, the header can only narrow a person to a shopper, the browser proxy forwards an allow-list of headers that does not include it, sessions rotate on sign-in, cookies are HttpOnly/Secure/SameSite=Lax, CSRF and redirect checks are allow-list based, webhooks are signature-checked, the SSRF guard on media URL fetches is thorough, and the seed/demo guards exist for identity and content.

**It is not yet "zero known vulnerabilities", and four things should be fixed before real customers:**

1. **Known, reachable vulnerabilities today in every Go service of the launch set** (govulncheck, run for this audit): Go standard library `GO-2026-6859` (HTTP/1 server crash via `MaxBytesReader` race, fixed in go1.27.4; an unauthenticated crash/DoS class) and `GO-2026-6809` on go1.27.2, plus seven reachable `excelize` advisories in gateway-bff. CI would not have blocked these (gates fail only on CRITICAL).
2. **Per-IP rate limits can be bypassed by sending your own `X-Forwarded-For`** (the web proxy prefers the client's header, the BFF trusts its first hop), and the Cloudflare auth rate-limit rule uses paths (`/v1/auth`) that the real URLs (`/api/bff/v1/auth/...`, `/bff/v1/auth/...`) do not start with. Identity's per-IP counters use the proxy address, not the visitor's.
3. **Actuator/Prometheus and Go `/metrics` endpoints are reachable from the internet** by a path prefix (`api.afrotransact.com/identity/actuator/prometheus`, `/bff/metrics`, ...): the Cloudflare block rule only matches paths that *start with* `/actuator`, and the services treat these paths as public. (Swagger/Scalar/Redoc/`/v3/api-docs` are switched off in every prod profile.)
4. **CSP is `report-only` in production** on all three web apps, so it protects nothing yet.

**What is a risk but accepted-by-design today:** OpenFGA is off in prod (`FGA_ENABLED=false`) and not deployed, so cross-organisation isolation rests on the signed JWT `org` claim alone (it does hold in the code paths sampled; one layer, no second check). No Kyverno signed-image admission in the lean prod platform. No antivirus on uploads. Postgres TLS is `require`, which does not verify the server certificate.

**Could not be verified:** anything live (Cloudflare managed-WAF behaviour, header handling through Workers/tunnel/Envoy, Layerbase TLS/mTLS/backups, OVH), Java dependency vulnerabilities (OWASP Dependency-Check needs an NVD key and was not run; no Trivy/osv-scanner installed), container image CVEs, GitHub repository/branch/environment settings, whether `NVD_API_KEY` is configured, and a full IDOR sweep of every endpoint.

## 3. Q1 Acting-as (verdict: SECURE for production; dev-only breakage remains)

Mechanism: `client.go:374-379` sets `Authorization` and, when `port.IsShopper(ctx)`, `X-Acting-As: CUSTOMER`, for **any** request that has a bearer, including a service token. `actingContext` marks every route except `/v1/seller/*` and `/v1/staff/*` as shopper (`middleware.go:207-217`).

Call sites that fetch a service token (all send the header whenever their request context is a shopper request):

| Call site | Scope | Upstream | In launch set | Header sent with service token? |
|---|---|---|---|---|
| `app/stockalert.go:145` | guest stock-alert scope | notifications (Go) | yes | yes (public route) |
| `app/careers.go:41` | "" (all scopes, F14) | content (Java) | yes | yes |
| `app/membership.go:91` | "" (all scopes, F14) | payments (Java, membership tiers) | yes | yes (guest only) |
| `upstreams/local_delivery.go:36` | variable | delivery-runs (Java) | no | yes |
| `upstreams/pay_links.go:37` | pay-link | orders (Java) | yes | yes |
| `upstreams/native_signin.go:29` | first-party | identity (Java) | yes | yes |
| `upstreams/proof_links.go:37` | `media:read` | media (Go) | yes | yes |
| `upstreams/shopper.go:566` (tracking) | `shipping:rate` | carrier-gateway (Go) | no | yes |
| `upstreams/seller_commerce.go:511` | `payments:fees.read` | payments (Java) | yes | yes on storefront routes; no on `/v1/seller` and `/v1/staff` (unmarked) |
| `upstreams/session_policy.go:38` | session-policy scope | identity (Java) | yes | yes |
| `upstreams/shopper.go:153` tax quote | `tax:quote` | tax-returns (Java) | yes | **no**, fixed by `4f7128f1` (`WithoutShopper`) |

Production behaviour: identity always writes `pt=SERVICE` on client-credentials tokens (`IdentityTokenCustomizer.java:63`; `SelfIssuedServiceToken.java:46`). Java `ActingAsActorResolver.PEOPLE` and Go `actsAsCustomer` (`go/pkg/auth/acting.go`) contain CUSTOMER, SELLER_MEMBER, PROVIDER_MEMBER, DRIVER, STAFF only, so `ActingAs` returns a SERVICE actor unchanged (unit tests `acting_test.go:60,92`, `ActingAsActorResolverTest.java:117`; the Go auth tests and the Java resolver tests were run and passed). Both implementations are the same. So **no prod authorisation decision differs** for these calls. Caveat: Java defaults a token with no `pt` claim to CUSTOMER (`JwtActorResolver`, Go `verifier.go:101`); identity never issues one without `pt`, but a future token source that omits it would be narrowed.

Local only: `LocalActor` maps any non-person token (including SERVICE) to the STAFF super admin with `*`; `ActingAs` then turns that STAFF actor into a CUSTOMER with only `mcp:shopper`, so any local upstream that checks a permission returns 403. That is the trigger bug; the other sites in the table are exposed the same way wherever the upstream calls `require(permission)`. See F16.

Can a shopper-supplied header widen privilege? **No.** `ActingAs` only filters: type becomes CUSTOMER, org dropped, roles reduced to `account.*`, STAFF permissions reduced to `mcp:shopper`, same subject; other values and non-person types return the actor unchanged. The BFF never reads `X-Acting-As` from the inbound request (`grep` shows it only in `httpclient/client.go` and the comment in `middleware.go`), and it does not copy inbound headers upstream (no `Header.Clone`/range over `r.Header`; each upstream builds its own header set). The Next.js `/api/bff` proxy forwards an allow-list (`BFF_PROXY_FORWARD_REQUEST`: geo hints, accept*, content-type, cookie, idempotency-key, if-*, origin, user-agent, x-background, correlation ids) and never `Authorization` or `X-Acting-As` (`correlation.ts:32-50`). Java services that browsers can reach directly (`/identity`, `/bookings`, `/fulfilment`) do read `X-Acting-As` from the browser, which is safe because it can only reduce. No service trusts an `X-User`/`X-Org`/`X-Role` style identity header: the only custom headers read in Java/Go are the product ones (`X-Guest-Cart`, `X-Step-Up` proof, `X-Crawler`, `X-Home-*`, webhook signatures).

## 4. Q2 at.security.enabled (verdict: SECURE today, single point of failure, F5)

- False **only** in `application-local.yml` of ai-gateway, bookings, catalog, content, delivery-runs, fulfilment, inventory, mcp-server, offers, orders, payments, retail, seller, tax-returns, trust-ops (YAML scan of every `application*.yml`). Identity sets it `true` in `application.yml`. Default when unset is `TRUE` (`PlatformSecurityProperties.java:21`). No prod/uat file sets it.
- `AT_SECURITY_ENABLED` appears in exactly one values file, `mcp-server/deploy/helm/values-prod.yaml:20`, set to `"true"`, and mcp-server additionally refuses to start with it false (`McpExposureGuard.java:35`). It does not appear in ArgoCD, workflows, compose or the library chart.
- `LocalActorResolver` is selected only by `props.enabled() ? JwtActorResolver : LocalActorResolver` (`PlatformSecurityAutoConfiguration.java:41`). With security enabled it is not reachable. It is present in prod images (the local yml and class ship in the jar), but the image sets `SPRING_PROFILES_ACTIVE=prod` (`java/Dockerfile:39`), the chart sets `SPRING_PROFILES_ACTIVE` to the environment (`_helpers.tpl:75`), and CI asserts `required-env: SPRING_PROFILES_ACTIVE=prod` on image builds (`_java-service.yml:227`, `ovh-images.yml:70`). Only a service-level `extraEnv.SPRING_PROFILES_ACTIVE` override (used for `uat,temporal-cloud` in orders) could replace it; none exists for prod.
- Seed and demo: identity's bootstrap admin and test users are policy-guarded (`LocalDevelopmentPolicy`, `checkedBootstrapAdmin`, `testUserSettings`: refuse uat/prod, a `.test` address or a published local password, minimum length); delivery-runs `DemoAreaSeeder` is `@Profile("local")`; the `seed-guard` workflow and `tools/seed` tests keep demo home content out of prod/uat/trial. Not run live.

## 5. Q3 OpenFGA (verdict: RISK, Medium, F6)

`at.security.fga.enabled/enforce` default `false` in `application-prod.yml` of catalog, offers, orders and payments. With it off, `ResourceAccessChecker` is `RbacResourceAccessCheckerImpl`: the RBAC permission **and**, for org-owned resources, `requireForOrg(permission, ownerOrgId)` (non-staff must carry the same `org`). The relationship layer (membership from the store instead of the JWT claim, per-resource relations such as platform view-all, shadow vs enforce) is disabled. authz-sync and OpenFGA are not in the launch set (`secrets.sh:28`). Exact risk: any bug in the identity `org` claim or in a service that forgets `requireForOrg` is not caught by a second layer; stale claim until expiry (5 minutes) after removing someone from an organisation. Not seen: an actual cross-seller bypass.

## 6. Q4 Service-to-service auth (verdict: SECURE with notes)

- Scopes per client (identity `application-prod.yml`): no wildcards and no `*`; each service has a short, purposeful list. Broadest: trust-ops-service (`catalog:moderate`, `compliance:hold`, `offers:write`, `sellers:enforce`, `orders:lookup`, `payments:service`, `users:read`, `ai:triage`, `bookings:reviews:moderate`), gateway-bff (first-party sign-in plus 7 read/quote scopes), orders-service. Public clients require PKCE (`StartupProvisioning.java:111`), refresh tokens rotate (`reuseRefreshTokens(false)`), access tokens default 5 minutes, refresh 30 days (driver app 14 h). Redirect URIs are exact strings.
- Secrets: every client secret comes from an env var with no default in prod except `GATEWAY_BFF_CLIENT_SECRET`, `SELLER_SERVICE_CLIENT_SECRET`, `CATALOG_CLIENT_SECRET` (empty default; a blank secret makes identity skip the client, fail closed). Base-file `local-*` defaults exist (F15) but are either overridden without default in prod or unusable. Not verified live: that every `*-secrets` object contains the names the apps expect (the apply script refuses empty mandatory ones).
