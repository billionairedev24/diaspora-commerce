# release-1 parity: done on main is not done until the monolith has it

**The rule.** `release-1` (the modular monolith, ADR 0011) is what goes to production. `main` and `develop` keep the per-service build
for the microservice option. **A change on main or develop is not done until release-1 parity is green**: whatever it adds (a service,
a route, a migration, a Kafka consumer, a setting, a scrape, a workflow) must also exist in `afrotransact-core` or `afrotransact-go`,
automatically and verifiably. "Verifiably" is `tools/release/parity.py`, which runs on every release-1 pull request, on every sync pull
request and on `make release-1-check`.

The runbook for the branch model, the settings the owner changes and the hotfix flow is
[release-1-deploy.md](../runbooks/release-1-deploy.md) (sections "Branch model" and "Settings the owner changes").

## How a change on main reaches production

```
 main / develop ──(daily, or by hand)──► release-1-sync workflow
                                           │ sync/main-<sha> cut from release-1, merge, mechanical resolution
                                           ▼
                                  pull request into release-1  ──►  core, afrotransact-go, release-1-parity (required checks)
                                           │ red = a gap: the table in the job summary says what and how to fix it; push the fix to the branch
                                           ▼ green + review
                                       release-1 ──► Argo CD (dev auto, uat auto, prod manual) ──► production
```

* **The sync** (`.github/workflows/release-1-sync.yml`, `tools/release/sync-open-pr.sh`, `tools/release/sync-main.sh --ci`) merges main (and
  develop on request) into a throwaway `sync/` branch. It resolves only what is mechanical and reports everything else:
  * `docs/backlog/backlog.csv` is merged **by row** (`tools/release/merge_backlog.py`): append-only, release-1's stories live in S600-S699
    (epic E37), an id that collides with a different row from main renumbers the **release-1** row (its epic children follow), the same field
    changed two ways is a conflict. A line-based merge corrupts this file (multi-line rows interleave), which is why it is never merged by line.
  * generated workflows (`java-*.yml`, `go-*.yml`, `web-*.yml`, `promote.yml`) are regenerated by `tools/ci/gen_workflows.py` when they are the only conflict.
  * the service charts' new settings are carried into the deployable charts (`tools/release/chart_env_sync.py --write`).
  * every other conflict opens **one issue** listing the files (with a hint per file) and nothing is pushed.
* It never pushes to release-1, main or develop, never forces, and pushes only `sync/*`.
* The pull request is titled with the commits it carries; it is a **draft** while `parity.py` has gaps.

## What `parity.py` checks

`python3 tools/release/parity.py` (state of the tree) or `--main origin/main` (also marks which gaps come from what main changed since the last
sync). Output is a table of gaps with a one-line fix hint each (`--format markdown` for the job summary).

| Check | Fails when | Fix hint |
|---|---|---|
| `mounted-java` | a `java/services/<s>` directory is not a `@ModuleSpec` of `CoreApplication` (or core's pom lacks its jar) and not listed under `unmounted.java` in `parity.yaml` with a reason | mount it as a module (checklist below) |
| `mounted-go` | a `go/services/<s>` directory is not in `go/apps/afrotransact-go/internal/registry` and not under `unmounted.go` | add the `host.Spec` |
| `routes` | a route main added or changed in `contracts/openapi/<module>.yaml` of a mounted module is one the core route diff (`route_diff.py`, run by `core.yml`) says core does not answer | implement/fix the mapping in the module |
| `migrations` | a Flyway migration of a mounted module runs `CREATE EXTENSION` of an extension the bootstrap does not pre-create, references another module's schema, or creates schemas/roles/databases, `GRANT`s to a named role, `SET ROLE`s | add the extension to `release-1-bootstrap.sql`, or call the other module's `api` package |
| `kafka` | a `@KafkaListener` has no explicit group, a group that is not `<module>-service[-suffix]` (core would split offsets), a standalone `group-id` override, or a topic not declared in `contracts/asyncapi/events.yaml` | `groupId = "${spring.kafka.consumer.group-id:<module>-service}"`, declare the topic |
| `config` | a service chart's `extraEnv` is not in the deployable chart (generated block out of date), two modules set one name to different values, a mounted module has no `modules.<m>` entry or `MODULE_<M>_ENABLED` switch | `python3 tools/release/chart_env_sync.py --write` |
| `secrets` | a Secret key a service chart documents (`# - NAME`) is not rendered by `infra/ovh-vps/secrets.sh` | add `NAME=` to the module's branch of `service_keys()` |
| `observability` | a rule, dashboard or scrape config selects `service="x"` where `x` is not a module, a deployable or a platform component | use a module short name (the monolith keeps tagging meters with it) |
| `delivery` | a per-service Dockerfile/chart/workflow for a service that is not a module in `release-1.yaml`; a service missing from `services.conf`; a workflow nobody classified in `parity.yaml` (`release-1`, `per-service-only`, `manual`, `reusable`) or whose triggers contradict its class; a workflow, `Chart.yaml` or values file that is not valid YAML | classify it; make it trigger on release-1 |
| `http-edges` | a new always-on `Http*` adapter under `adapter/out` that is not in `java/apps/core/src/test/resources/http-edges.txt` (the static twin of `ModuleEdgeGuardTest`) | add an in-process adapter and `@ConditionalOnModuleMode`, or list it with the reason |

### The other direction: `--reverse`

`python3 tools/release/parity.py --reverse --main origin/main` (`tools/release/reverse_parity.py`, tests `test_reverse_parity.py`) answers "what does release-1
have that main lacks". It compares the Flyway migrations (file sets and contents), `contracts/**`, the permission seeds (`*Permissions.java`, identity's
`Permission.java`, the tenant-isolation matrices) and the i18n keys of web and mobile, and labels each difference by who changed it since the merge base:
`port-back` (release-1 changed it: port it with `tools/release/port-back.sh`), `sync-pending` (main is ahead: the next sync brings it) or `both`. It is a
report: exit 0 unless `--strict`, and `release-1-parity.yml` runs it as a non-blocking step with a warning when something has to be ported back. A
difference that is intentional goes under `reverse_skip` in `parity.yaml` (glob: reason).

`parity.yaml` is the allow-list: `unmounted` (service, reason), `per_service_only`, the classification of every workflow, `config.env_skip` and
`secret_skip` (name, reason). An entry without a reason does not count.

Other offline gates in `make release-1-check`: `check_launch_set.py` (Applications per environment, `release-1.yaml` vs `cutover.services`, **every
ApplicationSet generator reads release-1**), `check_delivery.py` (pools, modules, `service=` labels), `check_capacity.py` (the plan fits the one b3-16
node at every batch, with core's rolling-update surge), `chart_env_sync.py`, the generated workflows, action pins, shellcheck, the tests of all of the above.

### Re-running a full branch diff audit (main / develop vs release-1)

(From the former `branch-diff-audit.md`, section 5; that one-off audit found 0 functional differences to port back.)

```
git fetch origin main develop +refs/heads/release-1:refs/remotes/origin/release-1
git cherry origin/main origin/release-1 | grep '^+'                  # step 1: commits main lacks (by patch id)
python3 tools/release/parity.py --reverse --main origin/main         # on release-1: migrations, contracts, permissions, i18n, direction-labelled
git diff --name-only $(git merge-base origin/main origin/release-1) origin/release-1   # then compare each non-architecture file with main
```

On release-1 `parity.py --reverse` (`tools/release/reverse_parity.py`) automates the four functional comparisons and is a non-blocking step of `release-1-parity.yml`.

## Contributor rules

1. **Working on main or develop?** Open the PR as usual. Before you call a story `Done`, look at the next sync pull request (or run
   `python3 tools/release/parity.py --main origin/main` on a release-1 worktree after `tools/release/sync-main.sh`). If it names a gap from your change,
   the story is not done. Fix it on the sync branch (or in a release-1 PR) and set `Done` once release-1 parity is green.
2. **Working on release-1?** The check `release-1-parity` is required; a change that adds a service, a route, a migration, a setting or a workflow
   without its monolith side fails it, whatever branch it came from.
3. **Hotfix?** Fix it on release-1 (production line), then port it back with `tools/release/port-back.sh` (a cherry-pick PR to main/develop), so the two
   lines never drift ([branch model](../runbooks/release-1-deploy.md)).
4. Never edit `docs/backlog/backlog.csv` conflict markers by hand: `tools/release/merge_backlog.py` (or `tools/release/setup-merge-driver.sh` once per clone).

## Adding a new service as a module (release-1-architecture.md section 9, expanded)

A service added on main or develop shows up as `mounted-java` / `mounted-go` and `delivery` gaps on the next sync. The module batch, in order:

1. `<m>-api` jar with only what other modules call; the provider adapter in `adapter/in/module`; an in-process adapter for each outbound port that calls
   another module over HTTP, chosen with `ConditionalOnModuleMode` (`at.<caller>.<callee>.mode`; default `in-process` in core, `http` standalone).
   An adapter that stays HTTP (to a Go service, or to a module that is off) goes into `http-edges.txt` with the reason.
2. `plain` jar and `modules/<m>/` resource copies in the service pom; `@ModuleSpec(name, service, basePackage, ...)` in `CoreApplication`; the
   `<m>-service` (classifier `plain`) dependency in `java/apps/core/pom.xml`. Go: `module.go` (`Name`, `New`) and the `host.Spec` in `registry.go`.
3. Scope the `@RestControllerAdvice` by package and check every `static` singleton; ArchUnit stays green.
4. Caller scopes in the in-process registry, copied from identity's client entry for that service (S6 test: 403 without the scope).
5. Core config: `MODULE_<M>_ENABLED` in core `application.yml`; the module in `infra/argocd/launch-set/release-1.yaml` (`deployables.*.modules`) and in
   `modules:` of the deployable chart (`schema`, `pool`, `schedulerPool`, `modeEnv`); the schema and pool in `infra/ops/postgres/release-1-bootstrap.sql`
   (the pool in chart and SQL must agree: `check_delivery.py`); a line in `infra/ovh-vps/services.conf` and a branch in `service_keys()` of `secrets.sh`.
6. Settings: they live in the **service chart** (`extraEnv` in `values.yaml` and `values-<env>.yaml`, secret names in the `# - NAME` comment); then
   `python3 tools/release/chart_env_sync.py --write` copies them into the deployable chart (a generated block; never edit it by hand). A name that the
   deployable computes itself (database URL and pool, JVM flags) goes under `config.env_skip` in `parity.yaml` with the reason.
7. Tests: the module's own suite, ArchUnit, the in-process 403 test, `route_diff.py` (the contract route diff), `KafkaGroupIdsTest`.
8. Dashboards and alerts select on the module's short name as `service=`; nothing to change unless a label rule moves.
9. `python3 tools/release/parity.py` and `make release-1-check` green; set the backlog story `Done`.

## How new env or config reaches both charts

| What | Where it is written | How it reaches the deployable |
|---|---|---|
| A non-secret setting (peer URL, zone, TTL, flag) | `extraEnv` of `<runtime>/services/<m>/deploy/helm/values*.yaml` | `chart_env_sync.py --write` (the sync PR does it by itself; `parity.py config` fails until it is done) |
| A secret | the `# - NAME` list of the service chart and `service_keys()` in `infra/ovh-vps/secrets.sh` | the Secret `afrotransact-core-secrets` / `afrotransact-go-secrets` is the union of the modules' keys (`envFrom`); multi-line values (PEM) are one key |
| A module switch, pool, mode | `modules.<m>` in the deployable chart (and the SQL for a pool) | rendered as `MODULE_<M>_ENABLED`, `<M>_DB_POOL_SIZE`, `AT_<X>_MODE` by the chart template |
| A Kafka consumer | `@KafkaListener` with the standalone group | same code in core; `parity.py kafka` and `KafkaGroupIdsTest` |
