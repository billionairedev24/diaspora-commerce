# infra/observability (Release 1: the monolith)

Monitoring config for the two deployables of Release 1 (ADR 0011): **afrotransact-core** (Java, every module, local `:8120`) and
**afrotransact-go** (Go, every module, local `:8200`). A module is a label, never a port or a job.

## Series contract

| Series | Labels | Source |
|---|---|---|
| `http_server_requests_*` (Java), `http_server_requests_total` / `http_server_request_duration_seconds_*` (Go) | `module` = `service` = the module's short name (`orders`, `cart`), `env` | module-core `ModuleMeterFilter`; Go `internal/host/metrics.go` |
| `hikaricp_connections_*` | `pool` = `module` = `service` = module | module-core (pool name = module) |
| `kafka_*` client metrics, business meters | `module` by client-id / meter-name prefix | `ModuleMeterFilter` |
| `at_module_up` | `module`, `service` (= module); 1 = ready | module-core `ModuleUpMeter`; Go `moduleUp` collector (the same checks as `/readyz`) |
| `jvm_*`, `process_*`, `go_*`, `up` | `service` = `job` = `afrotransact-core` / `afrotransact-go`, `module` = `core` / `afrotransact-go` | process level, one per deployable |
| `tasks_scheduled_execution_seconds_*` | `code_namespace` (owning class; its package gives the module) | Spring scheduled-task observation |

Rules and dashboards select `service="<module>"` for module series and `job="afrotransact-core|afrotransact-go"` for the process.
`scripts/check_monolith_series.py` (part of `make observability-check`) fails when a rule or panel selects a `service` that is neither a module
nor a deployable, when `prometheus.yml` scrapes anything but core `:8120` and Go `:8200` as application targets (the legacy per-service ports
would count every request several times), or when the Alloy allowlist loses `at_module_up`.

## Files

| File | Purpose |
|---|---|
| `prometheus.yml` | local Prometheus: two application jobs (`honor_labels: true`) plus Postgres, Kafka, Valkey, Temporal, MinIO, Elasticsearch, OpenFGA and the observability stack. No Meilisearch job locally (its `/metrics` needs the master key; production Alloy scrapes it) |
| `otel-collector.yaml`, `tempo.yaml`, `loki.yaml` | local traces (tail sampling), logs and metrics pipeline |
| `otel-host-log-shipper.yaml` | tails `.local/logs/*.log`: `core.log` becomes `service.name` `afrotransact-core`, `afrotransact-go.log` stays; `module` is extracted into a log attribute where the line states it |
| `grafana/dashboards/*.json`, `grafana/provisioning` | generated by `scripts/generate_dashboards.py` (`make dashboards`); also written as ConfigMaps under `infra/k8s/platform/observability/dashboards` |
| `rules/*.yaml` | alert and SLO rules; `scripts/generate_rules.py` writes `slo-*.yaml` and the PrometheusRule CRs (`make rules`) |
| `alertmanager.yml`, `grafana-cloud/` | local Alertmanager (mailpit); Grafana Cloud routing (group by `alertname, env, service`) |
| Production scrape | `infra/k8s/platform/lean/alloy/config.alloy`: job `deployable_pods` (`honor_labels`, `sample_limit` 40000) and the metric allowlist |

## Checks

`make observability-check`: generated files fresh, monolith parity (above), dashboards are valid JSON, `promtool check rules`.
Not part of it and not run in CI here: `promtool check config` on `prometheus.yml` (needs a promtool that knows `fallback_scrape_protocol`, Prometheus 3.x),
`alloy validate`, `amtool check-config`, and anything against a running stack (see `docs/runbooks/release-1-deploy.md`, "Monitoring in production").

Dashboards: `at-release-1-modules` (start here: readiness, process, pools, connection budget against the 500 Layerbase limit, Kafka, scheduled jobs, Temporal,
traffic per module), `at-platform-overview` (RED per module), `at-jvm`, `at-go-runtime`, plus the business boards.
