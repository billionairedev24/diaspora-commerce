# tools/seed: local demo data and test users

`make seed` (`python3 tools/seed/seed.py`, Python 3 standard library only) fills a local (or dev) stack through the
services' public APIs: sellers and providers, ~75 products with real photos, offers, stock, home content, sponsored
products, pre-order windows, the providers' services, the operations data (below), and a check of the test users. Every
step is idempotent, so re-run it any time; `make up` runs what is missing by itself (everything on an empty catalogue,
else the operations data). Full guide: [docs/engineering/local-development.md](../../docs/engineering/local-development.md).

```
python3 tools/seed/seed.py                      # every step
python3 tools/seed/seed.py --only ops           # just the operations data (make seed ARGS="--only ops")
python3 tools/seed/seed.py --only users         # just check the test users
python3 tools/seed/seed.py --skip products      # everything else
make seed-test                                  # the seeder's unit tests
```

Steps: `sellers`, `size-charts`, `products`, `content`, `ads`, `preorders`, `pickups` (AfroTransact's customer pickup points in
carrier-gateway, CARRIER_GATEWAY_URL), `bookings`, `ops`, `users`. The datasets are
`seedlib/dataset.py` and `seedlib/ops_dataset.py`; photo sources, attribution and service URLs are described in
`seed.py` and the guide.

### Guards (never against production)

`seed.py` stops before any step when `APP_ENV`, `ENVIRONMENT`, `DEPLOY_ENV`, `SPRING_PROFILES_ACTIVE` or `ENV` names prod,
production, uat or staging; when any service URL it uses (`CATALOG_URL`, `AUTH_ISSUER_URL`, ...) has a host under
afrotransact.com other than the dev environment's (`dev.afrotransact.com`, `*-dev.afrotransact.com`; never the trial's `*-test.`, which runs the prod profile) (this holds even with
`SEED_ALLOW_REMOTE=1`); and when a URL is not on this machine unless `SEED_ALLOW_REMOTE=1` is set. Hosts are parsed, so
`localhost.example.com` or a path containing `localhost` is not local. `tests/test_guard.py` covers it.

### Departments of the demo sellers

A seller may only create and edit items in the catalog departments recorded for its organisation (docs/engineering/seller-catalog-scope.md).
The `sellers` step therefore sends each marketplace seller the departments of the products it lists
(`seller_departments()` in `seedlib/dataset.py`: its own products and the ones it offers next to another seller), as the
catalog's department node codes read from `GET /v1/categories` (nothing is hard-coded per category). seller-service adds
them on every call, also to organisations seeded earlier, and never removes one, so a re-run keeps every demo seller
consistent with its products. Providers and AfroTransact Retail (exempt) get none. The seeder itself writes the catalog
as AfroTransact Retail, which is exempt, so seeding never depends on a seller's departments. The seed assumes an empty
database (there is no legacy handling): wipe, then seed.

### Size charts and sizes of their own

The `size-charts` step writes the demo size charts (`SIZE_CHARTS` in `seedlib/dataset.py`: women's dresses, women's tops,
men's shirts and kaftans, kids' party dresses) through catalog's `POST /v1/size-charts`, as the seeder's own organisation
(the same one that owns the demo products). It finds a chart by name first, so re-running writes nothing, and the
`products` step does the same when it runs alone. Fashion products name their chart (`chart=`, and optionally their own
`fit=`); the listing is created with `listing.sizeChartId` and `fitNote`. Two products show sizes and colours the category
does not list (`adire-shift-dress`: "UK 12", "Free size", "Indigo adire"; `sequin-gele`: "Champagne", "Teal & gold"), which
needs the sizing configuration of the catalog (see *Sized product types* below). A product that already exists keeps
its content, but a re-run links its chart and fit note through catalog's edit (the report line "product size charts"
shows `linked` or `existing`); if catalog refuses the edit (for example a size the chart has no row for) it is reported
as a problem and the run goes on. `tests/test_dataset.py` checks
the charts against catalog's rules and that every size a product sells has a row in its chart.

## The category tree is not seeded here (category tax tree)

The department > category > product type tree and each product type's details are the catalog service's initial
data (`V1_1__initial_data.sql` of the catalog baseline, generated by `tools/taxonomy/gen_catalog_baseline.py`; the detail
questions come from `catalog_taxonomy.py`, which writes `schemas.json`). They are managed by staff in the console
(Catalog > Categories) or the importer from then on, so this seeder only reads the tree to place its demo products and never edits it.
See [docs/engineering/taxonomy.md](../../docs/engineering/taxonomy.md).

## Sized product types

The fashion product types are sized (the `sizing` trait with suggested measurements) and let sellers write their own Size
and Color values (`allowCustomValues`); the data lives in `CUSTOM_DIMENSIONS` and `SIZING` in `catalog_taxonomy.py` and
reaches the catalog through `schemas.json` (initial data and importer). See `docs/engineering/size-charts.md`.


### Tax review of the demo data, and the Retail offer wait

**Tax review.** The staff setting `taxReview.mode` is `RISK_BASED` by default, so the rules approve a plain grocery such as Basmati
Rice themselves (actor `auto`) within seconds, with no click; the seeder then finds nothing to approve for those. What follows is the path
when the mode is `ALL` (`TAX_APPROVAL_POLICY` applies only then, default `ALL`) and for the exceptions the rules send to a person: every
variant catalog reports gets a classification record in `PENDING_REVIEW`, and catalog marks the variant `PENDING_REVIEW` too
(log line `Variant ... tax status READY -> PENDING_REVIEW (tax-returns)`). The product stays LIVE, visible in listings and
search and has its offers, but **checkout cannot charge it**: tax-returns quotes a line only when its record is `APPROVED`
(`LineDecisionServiceImpl.early`: `NEEDS_APPROVAL`, "not approved"). So the `products` step acts as a tax reviewer, like
the Tax Reviewer test user would: after the products it lists the review queue
(`GET /v1/tax/variant-classifications?status=PENDING_REVIEW`) and approves each seeded variant whose decision is
`RESOLVED` with the reason *Demo data approved by the seeder* (`POST .../{atin}/approve`). It never approves a record
whose decision is `MISSING_FACTS`, `BLOCKED`, `NEEDS_APPROVAL`, `REFINE_CODE` or `CONFLICT_OPEN`; those are reported.
Records reach tax-returns over Kafka, so the queue is polled for up to 60 s (`SEED_TAX_REVIEW_WAIT`). If catalog's
publish gate refuses `approve` because the variant already flipped to review, the seeder reviews it and retries.
Locally security is off and no token is needed; with security on set `SEED_TAX_TOKEN` to a Tax Reviewer's access token
(permission `tax:classify-admin`, role *Tax Reviewer*, `staff.tax@afrotransact.test`), or register the seeder client with
the scopes `tax:read tax:classify-admin` and list them in `SEED_SCOPES` (which replaces the default scope list). `TAX_APPROVAL_POLICY=SENSITIVE` would also work locally but only auto-approves
plain taxable items, so the seeder approves instead.

The seeder works in both review modes. With the staff setting `taxReview.mode` = `RISK_BASED` (Settings → Sales tax → *Review settings*;
off by default) the system approves many variants itself (`classifiedBy` `auto`), so they never appear in the queue: the seeder counts
them as *approved by the system (risk-based review)* instead of waiting for them, leaves audit sample items (live, waiting for a person
to confirm) alone, and if a record is approved by the system between the listing and its own approve call it re-reads the record
instead of failing the run.

**Retail offer.** AfroTransact Retail's offer is created by offers from the Kafka event `catalog.product.created`. On a cold
stack the consumer group can take a while to join, so the seeder waits up to 120 s for the first Retail product
(`SEED_RETAIL_OFFER_WAIT`), then 20 s for the rest once one arrived (or after a timeout, so a dead Kafka path does not cost
120 s per product). If it still fails: *offers did not create the Retail offer from catalog.product.created: check
`.local/logs/offers.log`, Kafka (`docker ps | grep kafka`) and run `make seed` again (it picks up where it stopped)*. A re-run finds
the product (looked up by title) and the offer that has arrived since, and carries on.

### Demo products in the category tax tree

The demo products sit in the 13 > 73 tree (`seedlib/dataset.py`: leaf paths, `CATEGORY_OF`), each with demo answers to its
category's questions (`seedlib/category_demo.py`, from `tools/taxonomy/category_tax_map.json`, sent as `taxFacts` per variant and
`listing.sellerBehaviour`). Every ACTIVE category has at least one demo product (the generated `demo-*` items are sold by
AfroTransact Retail) except *OTC medicines*, whose every valid answer needs a proof file the seeder cannot upload. Products in a
gated category (the provisional *Fabrics & textiles*, NEEDS_APPROVAL) are skipped with a note. The catalog imports the tree itself
(the baseline initial data and the start-up import); locally run the tax-returns service too, or set `CATALOG_TAX_RESOLVER=local` (the local default).
